CampusRide
A Scalable Smart Ride-Sharing System for College Students
System Design Project Report
Confidential — For Evaluation Use Only

1. Problem Statement
Students at our campus travel frequently to Jahangirpuri Metro Station and other nearby destinations. A  
cab costs approximately Rs 900 regardless of whether 1 or 4 people travel. Currently, students post in 
large WhatsApp groups asking if anyone else is going — but by the time someone sees and replies, the  
person has already left. There is no structured, time-aware coordination system.
Pain Point Description
Wasted Money Students pay Rs 900 alone when others may be going at the same time
No Coordination WhatsApp messages get buried; no time-based structure exists
Timing Mismatch No way to know in advance who is leaving at what time
No Confirmation No place to finalize pickup point, luggage, or meetup details
Trust Gap Cannot verify whether the person sharing is actually from campus
2. Solution Overview
CampusRide is a web-based, campus-only cab sharing platform. Students can post rides, discover 
others going the same way, join rides, split the fare automatically, and coordinate via a live in-ride 
group chat. Only verified college email addresses are accepted.
#Action What Happens
1Post a Ride Set destination, date, time, max seats (1–4), optional fare estimate
2Ride Goes Live Instantly visible to all campus students on the homepage feed
3Others Join Students going the same way request to join the ride
4Fare Splits Each person's share updates live as members join
5Group Chat Members discuss pickup point, luggage, and final details in live chat
6Creator Confirms Creator locks the ride — all members notified instantly via socket
7Completed Ride marked done; history saved for all members
Core Value: Up to Rs 675 saved per trip when 4 people share a Rs 900 cab (Rs 225 each). The 
platform enforces trust through college email OTP verification, ensuring all participants are 
verified campus students.

4. OOP Concepts Applied
CampusRide applies all four pillars of Object-Oriented Programming throughout its architecture. Each 
concept is applied intentionally — not superficially.
4.1 Encapsulation
Encapsulation hides internal implementation details and exposes only what is needed through a 
controlled public interface.
•The Ride class encapsulates all ride state (status, members, fare) and only exposes methods 
like join(), close(), cancel(), and getFareSplit(). External code cannot directly mutate ride status 
— it must go through these methods, which enforce state machine rules.
•The User class hides passwordHash completely. Authentication logic is encapsulated in 
AuthService — the only entity allowed to compare or generate hashes. Route handlers never 
touch raw passwords.
•Repository classes (RideRepository, UserRepository) fully encapsulate database access. No 
route handler touches Mongoose directly — it always goes through the repository layer, keeping  
database concerns isolated.
4.2 Inheritance
Inheritance enables code reuse by allowing classes to derive behaviour from a parent. CampusRide 
uses inheritance in two key hierarchies:
•Notification hierarchy: BaseNotification defines common fields (userId, isRead, createdAt, type) 
and an abstract send() method. RideJoinedNotification, RideConfirmedNotification, and 
RideCancelledNotification each extend it, inheriting all base fields and overriding send() with 
their specific message content.
•Repository hierarchy: BaseRepository provides generic findById(), findAll(), create(), and 
delete() methods. RideRepository and UserRepository extend it, inheriting all CRUD operations 
and only adding domain-specific queries.
4.3 Polymorphism
Polymorphism allows objects of different types to be treated through a shared interface, with each type 
providing its own implementation.
•Notification polymorphism: All three notification types are treated as BaseNotification objects by 
NotificationService. It calls send() on each without knowing the concrete type — each subclass 
handles dispatch differently.
•Filter polymorphism (Strategy): RideFilter is an interface implemented by DestinationFilter, 
DateFilter, and TimeWindowFilter. The ride feed applies any list of filters using filter.apply(rides) 
— adding a new filter type requires zero changes to the feed logic.

4.4 Abstraction
Abstraction hides complex implementation behind simple interfaces, exposing only what the caller 
needs. CampusRide applies this at three levels:
•FareSplitter: Abstracts all fare calculation logic. Route handlers call 
fareSplitter.calculate(totalFare, memberCount) — they never deal with division, edge cases 
(zero members), or rounding logic.
•SocketManager: Abstracts Socket.io complexity. The rest of the app calls 
socketManager.emitToRide(rideId, event, data) — it handles room management, broadcasting, 
and connection state internally.
•AuthService: Abstracts JWT and bcrypt. Callers use generateToken(user) and 
verifyToken(token) without knowing the algorithm, secret key, or expiry logic.
5. Design Patterns
CampusRide implements four industry-standard Gang-of-Four design patterns. Each was chosen to 
solve a specific recurring architectural problem.
5.1 Observer Pattern
Aspect Detail
ProblemWhen a ride event occurs (member joined, confirmed, cancelled), multiple parts  
of the system must react: send notifications, update the feed, emit socket 
events. Hardcoding all these creates tight coupling.
SolutionRide acts as the Subject (EventEmitter). NotificationService, SocketManager, 
and RideFeedUpdater are Observers that register independently. When ride 
state changes, it emits an event and all observers react.
Used In Ride lifecycle — member joining, ride closing, cancellation
BenefitNew reactions to ride events can be added without touching the Ride class at 
all.
5.2 Factory Pattern
Aspect Detail
ProblemDifferent notification types need to be created in many places across the 
codebase. Calling new RideJoinedNotification() everywhere spreads 
constructor logic and couples callers to concrete classes.
SolutionNotificationFactory.create(type, payload) handles all instantiation. Callers never 
use new directly — the factory decides which class to create based on the type 
string.
Used In All notification creation across RideService and NotificationService
Benefit Adding a new notification type requires changing only the factory, not callers.

5.3 Singleton Pattern
Aspect Detail
ProblemThe database connection (Mongoose Client) and Socket.io server must have 
exactly one instance across the entire application lifetime. Multiple instances 
cause connection pool exhaustion and event duplication.
SolutionDatabaseClient and SocketManager are implemented as Singletons — they 
create one instance on first access and return the same instance every 
subsequent call.
Used In MongooseClient (database connection), SocketManager (WebSocket server)
BenefitPrevents resource leaks, ensures consistent shared state, and avoids duplicate 
events.
5.4 Strategy Pattern
Aspect Detail
ProblemRides can be filtered by destination, date, time window, or available seats. The 
original logic was a tangled chain of if/else statements that was hard to test, 
extend, or combine.
SolutionEach filter type is a Strategy implementing a common RideFilter interface with a  
single apply(rides) method. The feed composes any combination at runtime.
Strategies DestinationFilter, DateFilter, TimeWindowFilter, SeatsAvailableFilter
BenefitFilters are independently testable and composable without touching the feed 
logic.

7. System Architecture
CampusRide follows a three-layer client-server architecture with a dedicated real-time WebSocket layer  
running alongside the REST API on the same server.
Layers
•Browser (React + Vite): Home, CreateRide, RideDetail, Chat, MyRides, and Auth pages. State 
managed via AuthContext, SocketContext, and Axios API Client.
•Server (Node.js + Express, Port 5000): REST API layer (/auth, /rides, /messages, /notifs) and 
Socket.io server running side-by-side. JWT middleware protects all routes. Service layer 
contains RideService, AuthService, ChatService, NotificationService, FareSplitter, and 
SocketManager.
•Database (MongoDB via Mongoose ODM): Five collections — users, rides, ride_members, 
messages, notifications. Repository pattern abstracts all data access. Repository pattern 
abstracts all data access.
Key Architectural Decisions
•The Socket.io server attaches to the same Express HTTP server so both REST and WebSocket  
traffic run on port 5000.

•Socket connections are authenticated with the same JWT token used for REST API calls, 
passed via socket.handshake.auth.token.
•Every ride has a dedicated Socket.io room named by its ride ID — events are scoped so only 
ride members receive updates.

13.2 Environment Variables
Create a server/.env file with the following variables:
•MONGODB_URI — MongoDB connection string (e.g. mongodb+srv://...)
•JWT_SECRET — Random secret key, minimum 32 characters
•EMAIL_USER — Gmail address for OTP dispatch
•EMAIL_PASS — 16-character Gmail app password
•PORT — Backend port (default: 5000)
Create a client/.env file with:
•VITE_API_URL — Backend URL (e.g., http://localhost:5000)
•VITE_SOCKET_URL — Socket.io URL (e.g., http://localhost:5000)
13.3 Setup Instructions
1.Clone the repository: git clone https://github.com/[team]/cabshare.git
2.Install backend dependencies: cd server && npm install
3.Install frontend dependencies: cd client && npm install
4.Create server/.env with the variables listed above
5.Start MongoDB connection and sync Mongoose models: node scripts/db-init.js

6.Start backend: npm run dev (runs on port 5000)
7.Start frontend: npm run dev (runs on port 5173)
8.Open: http://localhost:5173
